RISKS
- More refusals where there was silent success. This is the intent. It covers invalid phones, tag-only names, cleared required fields, STALE_FIELDS and STALE_BEFORE. Watch the 'edit.approve.stale_before' log count and the refusal codes in the first week.
- An import that changes phone, contact, CR or channel while a salesman's edit waits now sends that edit back instead of silently reverting the import.
  - The salesman re-enters his changes; GPS may need recapturing.
  - Approvers need the banner explained once.
  - Bulk approve reports it per item.
- False conflicts from how values are represented.
  - Mitigation: one sameEditValue is used by the builder, the submit, the direct write, the approval and the page. '' ≡ null ≡ undefined; dates compare by ms; the GPS companions are never compared; bases are the loaded raw values, so stored phones and CRs compare as stored.
  - Residual: a writer that only reformats a value (e.g. re-normalising it) makes open forms conflict once. That is the safe side.
- STALE_FIELDS lets a second Submit replace the newer value on purpose. A user who ignores the message can still overwrite, but now knowingly. For a salesman, the approver also sees before = the newer value.
- Every page open at the deploy gets FORM_OUTDATED once. Deploy outside field hours. Phone copies survive under the unchanged base rule. Drafts from before item 22 (no base) are dropped with the existing message: at least three days old, and not provably safe to restore.
- A salesman's Save draft with an emptied required field is now refused ('… cannot be removed'). Before, it was silently kept.
- Direct writes now hold the customer row lock, so they wait briefly behind a photo attach or import on the same customer. The lock order is lib/locks.ts's, so no new deadlock pair. It also fixes the branch-before-customer order the auditor flagged for branch-only direct writes.
- STALE_FIELDS returns live values only for fields in the actor's own patch, on branches he may edit. The approval page shows 'Now' values only in the reviewer's scope, so F04's exposure does not grow.
- Folding Persian digits makes more phones valid and matchable in imports. A re-run may hold back, as a shared phone, a row that loaded before. This is the right outcome.
- Clears and the import's sub-channel clear export to Temix as blanks. Whether Temix reads a blank as 'clear' or 'keep' is the open Q-temix-headers under F12 (owner's). The full-lane import does not requeue a channel change today, and this change does not add a requeue.
- The import sub-channel clear lowers that customer's completeness by 10.
- The one-off rescore visibly raises dashboard figures.
- The promote transaction writes a little more (one update per branch whose score changes), inside the 20 s budget. Large chains on their first post-deploy import are the worst case.
- Test churn: every submitEditAction fixture (about 24 calls in 3 integration files) moves to v2 in the same commit. Payload-pinning unit tests change too. enrichmentFormRendersError becomes an allowlist.
- On the approval page and in the change report, equipmentConfirmed rows show under the raw field name. The approval page maps the value to Yes/No; the change report prints 'true'/'false'.
