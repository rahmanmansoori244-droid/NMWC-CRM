## 1. [P1] Manager can create, take over, or disable org-wide credit approvers (ACCOUNTANT/FINANCE_MANAGER/GM), defeating the credit-chain separation of duty
**Where:** `lib/permissions.ts:229` · **Perspective:** authz

**Claim:** The user-administration trust boundary treats only MANAGER and STEWARD as protected tiers. Every user-mutation path in services/users.ts is gated by requireManager() plus canMutateUser(), but canMutateUser only blocks a MANAGER from acting on a MANAGER or STEWARD target — ACCOUNTANT, FINANCE_MANAGER, and GM (the org-wide / region-scoped approvers that make up the CREDIT create chain SUP→FM→GM→ACC) fall straight through to { ok: true }. createUserCore and updateUserRoleCore apply the same incomplete blocklist. The net effect: an ordinary Manager can mint new FINANCE_MANAGER/GM/ACCOUNTANT accounts, reset the password of (i.e. take over) existing ones, demote them, or disable them. resetPasswordCore sets a Manager-chosen password and bumps sessionsRevokedAt, evicting the real approver and handing the Manager a working login to an org-wide approver. Because the chain's separation-of-duty guard (canActOnStep) keys only on user.id, a Manager who controls FM, GM, and Accountant accounts can single-handedly walk a fraudulent high-credit-limit customer through every approval step, or simply DoS the entire credit-approval function by disabling its approvers. This is a privilege escalation: the same file deliberately reserves MANAGER/STEWARD provisioning to a Steward (out-of-band) to prevent exactly this, but leaves the higher-authority approval roles unprotected.

**Evidence:** lib/permissions.ts:229-234 — `if (actor.role === Role.MANAGER) { if (target.role === Role.MANAGER || target.role === Role.STEWARD) { return {ok:false,...}; } } return { ok: true };` — FINANCE_MANAGER, GM, ACCOUNTANT are not in the blocked set. services/users.ts:81-86 createUserCore blocks only `data.role === Role.MANAGER || data.role === Role.STEWARD`. services/users.ts:341-345 updateUserRoleCore blocks promotion only to `Role.MANAGER || Role.STEWARD`. services/users.ts:257-277 resetPasswordCore gates solely on canMutateUser() then writes a new passwordHash + mustChangePassword + sessionsRevokedAt for the target. Contrast lib/approval-chains.ts:63-78 where the CREDIT chain is SUPERVISOR→FINANCE_MANAGER→GM→ACCOUNTANT and FM/GM are 'GLOBAL' org-wide approvers, and lib/permissions.ts:180 where canActOnStep separation-of-duty only excludes by user.id.

**Scenario:** A Manager (regional people-admin) wants to approve a fraudulent CREDIT customer or sabotage approvals. Via /users they POST resetPasswordAction for the company's Finance Manager and GM accounts (canMutateUser returns ok:true), setting known passwords; the real FM/GM are logged out by the sessionsRevokedAt bump. The Manager logs in as each in turn and approves the FM and GM steps of a credit create-request (acting as the Supervisor-step region-manager fallback for step 0 themselves), then resets/takes over the region-scoped Accountant to clear the final step — pushing a high-credit-limit customer live with no genuine second party. Alternatively the Manager just disables all FINANCE_MANAGER/GM accounts (toggleUserActiveAction) to halt all credit onboarding.
